# 外部审查记录（2026-10-22，第一份）

> 来源：用户送审 `errwatch-20261022-送审包.zip` 后的书面意见。
> 第二份审计意见待补（用户称"还有一份"）。本文只记录第一份 + 我的分类，**不含行动计划**（等齐后统一排期）。

## 一、审计方的整体判断

- 项目已从「报错解码器」演化为「Windows 故障诊断与处置工具」；
- 最有价值的进展不是规则数量，而是把「环境坏了工具还能不能帮人」解决到架构层（L1/L2/L3 + 证据包）；
- 三层能力不可混：**解码正确 ≠ 根因正确 ≠ 修复安全**（这条我完全接受）。

## 二、审计认可的（4 项）

1. `unknown` 是产品能力而非失败：未匹配就 unknown、不自动路由、不触发修复。
2. L1/L2/L3 + 采集/分析分离：可异机分析、规则可单独迭代、可复盘。
3. 测试体系盲区的发现（`TranslateForApp` 拼 App 名破坏行首锚点）。
4. 修复器的安全意识（预览绑定、通配符拒绝、锁、审计失败拒执行、安全模式默认拒绝）。

## 三、审计的保留意见（按优先级）

| 级别 | 问题 |
|---|---|
| P0 | 诊断结论可信度：28 条回归 + 7 个真实样本组合，不足以证明"普遍可靠" |
| P0 | 用户建议是否**安全且可理解**：缺可读性/可执行性验证（审计给了 5 项可用性测试指标） |
| P1 | 证据链与离线分析鲁棒性：恶劣场景、证据损坏、错误路径、来源冲突、容量边界 |
| P1 | 核心逻辑一致性：query/report/UI 等路径可能仍有自行加载/复制 |
| P1 | 故障覆盖面的真实边界（事件日志只能看到一部分） |

## 四、我的分类与事实核查

| 审计项 | 我的判断 | 依据/说明 |
|---|---|---|
| 诊断契约（known / unknown / insufficient / conflict / collection-failed） | **接受**，架构级改动，先出设计再动手 | `unknown` 目前是一个桶；审计说得对：未知、证据不足、证据冲突、采集失败是四种情况 |
| 统一实现 | **已基本闭环**，与审计描述不符 | 当前所有入口均 `Initialize-ErrwatchCore`；query/notify 注释明确写"已改为 dot-source core"；审计引用的 `audit-core-merge` 是历史记录 |

## 五、审计的长期问题（我认同）

> 当规则越来越多、证据来源越来越多，会不会重新变成"只有作者知道为什么这样判断"？

审计给的答案：把核心资产从「规则库」推进到
**可追溯的诊断依据 + 可复现的判断过程 + 有边界的行动建议**。

这正好是「诊断契约」那一项要解决的问题。

## 六、待两份审计合并后一起做的事

1. 把两份意见合并成一份带编号的整改清单（P0/P1/可延缓）
2. 先做「诊断契约」设计（影响所有入口，不能随手改）
3. 再做 L3 安全矩阵（不改库，纯测试）
4. 可用性测试排在真人可用时

## 七、第二份审计（竞争力视角）

### 核心判断（我认同）

- errwatch 的差异**不是「别人没有 WinRE」**（Chainsaw/Hayabusa 也有离线分析），而是
  **把发现/解释/风险控制/行动整合成一条面向普通人的完整工作流**；
- **竞争力尚未被验证**（不是没有竞争力）——送审包能证明工程结构、使用背景、测试闭环、边界意识，
  不能证明「陌生用户能独立用起来」。

### 6 个优化点 + 我的分类

| # | 建议 | 我的判断 |
|---|---|---|
| P0-1 | 「我现在该怎么办」首页：只答三件事（有没有问题 / 最重要的问题 / 我现在做什么） | **接受，且优先级最高**。现在 7 个入口对普通人是选择困难；首页必须基于「诊断契约」才能做（同一件事） |
| P0-2 | 通知变成行动闭环（发现→提醒→复查→已处理） | **接受**。现有 notify 只报「新错误」，没有生命周期；去重不能只按文本（同文本可能来自不同程序/设备） |
| P0-3 | 规则生命周期（来源/范围/状态/误报/最后验证/作者） | **部分接受**：字段化现在就能做（成本低）；完整治理（弃用流程、CI）等开源后 |
| P1-4 | 诊断优先级与聚合（同一根因聚合、趋势、伴随症状分开、噪音折叠） | **接受**。本机 `DistributedCOM/10016` 就是典型噪音；聚合必须保留原始计数与关联依据 |
| P1-5 | 隐私优先反馈（不上传、最小材料、脱敏清单、预览后导出） | **接受方向**，但现在没有外部用户，可延后；先把脱敏清单写进契约 |
| P2-6 | 第三方贡献诊断包（模板+校验+样例+预期输出+误报说明+许可证） | **接受方向**，初期只做「规则贡献模板」，不做市场 |

### 3 个工程问题 + 我的补充

1. **分发可信度**：发布包 SHA-256 + 版本清单 + 变更日志 + 签名/身份；**规则更新与修复更新必须权限分离**（她这条完全正确）。
2. **修复器授权体验**：每个动作要能说清「改什么/影响什么/前置检查/失败怎么办」。
   **我的补充**：不是每个动作都适合统一 rollback —— 重启服务、清理日志、改配置的恢复语义不同，
   应该让**每个动作声明自己的恢复语义**（可回滚 / 不可回滚 / 补偿动作），而不是套一个万能回滚。
3. **维护成本**：她建议的指标是对的 —— 新增一条规则 = 匹配逻辑 + 中文解释 + 负例 + 回归样例 + 来源审查 + 兼容性检查。

### 我不同意的部分

- 「功能冻结一小段时间做陌生用户首用版」——方向对，但**冻结前必须先有首页**，
  否则冻结的是一个「没有首页的版本」。顺序应是：**先做首页 + 通知闭环 → 再冻结**。
