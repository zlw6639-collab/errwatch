# 恢复机会（Recovery Opportunity）设计与落地 — 2026-10-23

> 起点是用户的一个判断：
> **「崩溃发生的时间不可预测，所以真正有效的应急设计，不能依赖『提前知道它什么时候崩』。
> 不是预测故障，而是在正常工作时就持续保留恢复机会；故障发生后，再尽快把这些机会组织起来。」**
>
> 这份文档回答三件事：这个判断哪里对、工作流该长什么样、什么办法能真的救援。

## 一、先看一个实测（它决定主攻方向）

按旧 `core\recover.json` 的路径表，在本机 WZL 上探 6 个典型恢复目录：

```
[缺]  VS Code 热退出备份     %APPDATA%\Code\Backups
[缺]  VS Code 本地历史       %APPDATA%\Code\User\History
[缺]  Notepad++ 备份         %APPDATA%\Notepad++\backup
[缺]  Office 未保存文件      %LOCALAPPDATA%\Microsoft\Office\UnsavedFiles
[有]  Word 自动恢复          共 2 文件 / 近 7 天 0
[有]  用户 TEMP              共 0 文件
```

**6 个漏 4 个。** 用户真崩一次、点救援，大概率看到「没找到候选文件」——
而真相是「应用没装」或「路径猜错」，不是「内容没了」。

所以「持续保留恢复机会」的第一价值不是备份内容，而是：
**在故障发生前就知道，这台机器上这个程序的恢复机会到底存在不存在。**

## 二、判断对，但要把「保留」拆成两件事

| | 持续做（每轮 / 每会话） | 故障后才做 |
|---|---|---|
| 做什么 | **登记机会点**：哪个 app、哪类机制、目录在不在、最新文件何时改过（只看 mtime/size） | **取内容**：列出候选、读大小/时间、让用户复制 |
| 成本 | 每会话 2 次只读探针，零隐私（不读内容） | 一次性，用户点了才触发 |
| 失败代价 | 只是「不知道」 | 可能误导用户 |

如果字面理解成「持续备份」，就会变成磁盘 + CPU + 隐私的三重黑洞，直接违反「不侵入」边界。

关键洞察：**恢复目录与判据属于「应用知识」，不是用户数据**。所以持续登记几乎不花钱。
errwatch 真正的差异化不是备份能力，而是一座**应用恢复知识库 + 新鲜度判定器**。

## 三、工作流（四段）

```
① 正常期 Watching           ② 故障期 Triage          ③ 救援期 Recover        ④ 学习期 Learn
   （原来缺失，本轮补上）       （已有，补新鲜度）        （已有，补分档）          （可选）
   进程出现 → 拍基线            事件入队                 用户点开                记账
   进程消失 → 拍事后            用 lastSeenAt            按新鲜度分档            哪个路径真救到了
   → opportunity.json           划出崩溃窗口             旧文件默认折叠           用于校准路径表
```

### ① 正常期：每会话两次探针

- **进程出现** → 拍基线（此刻恢复目录里最新文件的 mtime）
- **进程消失** → 拍事后（此时才知道有没有留下恢复文件）
- 两次一比，得出：

| `opportunity` | 含义 |
|---|---|
| `NEW_DURING_SESSION` | 这次会话里新产生过恢复文件 —— **最值得抢救** |
| `NONE_NEW` | 有恢复文件，但没比会话开始时更新 |
| `VANISHED` | 原来有，现在没了（可能被程序清理） |
| `NONE` | 目录在但一直是空的 |
| `NO_MECHANISM` | 找不到它的恢复目录（多半没装 / 路径表过时） |
| `NO_BASELINE` | 哨兵中途启动，没有基线，说不清 |

为什么不去「每 5 分钟刷一次」：每会话两次已经够判断「这次有没有新机会」，
而常驻刷新会让一个只读工具变得可疑（磁盘 IO、杀毒告警、笔记本耗电）。

### ② 故障期：用「最后看到它还活着」的时刻划窗口

复用 P0-2 的覆盖声明数据（`lastSeenAt`）。窗口内 mtime 的恢复文件才是强证据。

### ③ 救援期：分档，而不是按时间倒序排

| 档 | 判据 | 用户看到 |
|---|---|---|
| `IN_SESSION` | mtime ≥ 进程 StartTime − 60s | 「本次会话（最可能是你刚丢的那份）」 |
| `EARLIER_TODAY` | mtime 在会话之前、但属于今天 | 「今天早些时候」 |
| `STALE` | 更早 | 默认折叠，只显示条数 |

> 只按 mtime 排序是不够的：**上周留下的 `.sv$` 会排第一，用户会以为那是自己刚画的图**——
> 这比「没找到」更坏。`errwatch-recover.ps1` 原来正是只排序不判龄。

### ④ 学习期（未做）

`feedback.jsonl` 已有基建。按 HANDOFF 原则 9：**只能校准路径表，不能当规则可信度**。

## 四、什么办法能真的救援（分档，别含糊）

### 真有效（几乎零风险，成功率最高）
1. **让应用自己的恢复机制生效** —— 崩溃后重开应用，多数会弹「恢复未保存的文档」。
   这条成功率远高于自己找文件，但前提是自动恢复**开着**。
   所以 errwatch 最该做的是**检查开关并提醒开启**，而不是替它做备份（doctor 已加这一段）。
2. **自动保存文件本身**（Office `.asd`、CAD `.sv$`、VS Code 热退出备份）——
   拿到就能打开或转换，关键是「怎么把它变成能用的文件」：
   - `.sv$` → **复制** → 副本改名 `.dwg` → 打开核对 → 另存为正式文件
   - `.asd` → 程序内「文件 → 信息 → 管理文档 → 恢复未保存的文档」
   - VS Code Backups 是内部格式，**不要手工改**，让 VS Code 自己恢复

### 有条件有效
3. Windows 文件历史 / 卷影 / OneDrive 版本历史 —— **只能救已保存过的旧版本**，救不回未保存内容，且要提前开

### 基本无效，应当劝退
4. WER dump / 内存分析 —— 告诉你怎么崩的，**救不回正在编辑的内容**
5. 「进程级 checkpoint / 内存快照」—— **Windows 没有 CRIU 这种东西**，做不到
6. 定时截屏 / 键盘记录 —— 隐私灾难，收益极低
7. 注入 hook 拦崩溃 —— 反作弊红线 + 稳定性双杀（与本项目既有边界冲突）

## 五、落地实现

### 新增 `core\opportunity.ps1`（唯一实现）

| 函数 | 作用 |
|---|---|
| `Get-ErrwatchRecoveryStrategy` | 按 app 从 `core\recover.json` 取策略（含 mechanisms / convert） |
| `Test-ErrwatchPathAllowed` | 白名单根判定（策略文件不能变成任意文件访问） |
| `Invoke-ErrwatchRecoveryProbe` | 只读探针，返回三态 + 摘要（`-IncludeItems` 才返回逐文件列表） |
| `Get-ErrwatchFreshness` | 单个文件的档位判定 |
| `Sort-ErrwatchCandidatesByFreshness` | 加档位 + 按档排序 |

**为什么必须只有一份**：sentinel（登记）、recover（展示）、doctor（检查开关）三处都要用同一套判据。
历史教训：同一程序在报告与 UI 给出不同结论，就是两处各写一份。

### 探针三态（「没找到」太笼统，用户没法据此行动）

| verdict | 含义 | 用户能据此判断 |
|---|---|---|
| `HAS_FILES` | 有恢复文件 | 有东西可捞 |
| `EMPTY` | 目录在但没文件 | 多半「自动保存没开」 |
| `GENERIC_ONLY` | 只有通用临时目录（`%TEMP%`） | **不能当证据**，多半没装 |
| `NO_DIR` | 目录都不存在 | 没装 / 路径表过时 |

`generic: true` 是这一版新加的标记：`%TEMP%` 永远存在，用它当「目录存在」的证据会把「没装」误判成「有机制只是没产生文件」。

### `core\recover.json` v2

- 路径按真实安装位置重写（Office 的 `.asd` 分 Word/Excel/PowerPoint；CAD 的 `.sv$` 在 `%TEMP%`）
- 新增 `mechanisms`：恢复机制 + 怎么检查开关（`registry` / `json` / `behavior`）+ 开启方式
- 新增 `convert`：「拿到文件后怎么变成能打开的东西」
- `generic`：标记通用目录

### 三个入口的分工

| 入口 | 写/读 | 职责 |
|---|---|---|
| `errwatch-sentinel.ps1` | **写** `opportunity.json` | 会话出现拍基线、消失拍事后 |
| `errwatch-recover.ps1` | 只读 | 分档展示、折叠旧文件、空结果说清三种之一 |
| `errwatch-doctor.ps1` | 只读 | **没崩的时候**就告诉用户「哪个恢复机制没开」 |

## 七、已知边界

1. **路径表仍会过时**：应用升级可能改目录。`NO_DIR` / `GENERIC_ONLY` 的措辞已承认这一点，但不等于自动修正
2. **只判断「有没有」，不判断「内容对不对」**：候选文件是不是你要的那份，仍然只能人看
3. **会话时间可能拿不到**（哨兵中途启动、进程已退出且无记录）→ 降级为按 mtime 粗分，且明确标注 `sessionKnown=false`
4. **`behavior` 型检查是推断**：近 7 天有恢复文件 = 机制在工作；没有 = 可能没开，也可能是这周没干活
5. **不发现在「程序正常关闭」时清理的恢复文件差异**：`CLOSED` 与 `LOST` 只记录，不据此下结论
6. **仍是合成夹具**：本轮没有真实 CAD / Office 崩溃样本，不宣称验证了真实恢复能力
7. **未做**：主报告 / UI 还没消费 `opportunity.json`（只有 recover / doctor 两处）
