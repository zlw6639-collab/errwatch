## 二、认可的进步

### 1. 修复器建立了执行契约

`Plan → Validate → Confirm → Revalidate → Execute → Verify → Record`

- `restart-process` 不再默认结束同名全部进程；新增 `-ProcId`；多实例默认拒绝
- 复核进程启动时间，防 PID 复用
- 限制当前会话，拒绝系统及其他用户进程
- `restart-service` / `restart-process` 标为高风险、不可逆，需额外确认

**但审阅方强调**：执行安全 ≠ 建议安全。
工具正确拒绝危险操作是执行安全；若**一开始就错误建议**结束关键进程，闸门再严也会误导用户。
→ 后续安全测试必须覆盖**建议生成**的整条链路，不能只测修复器。

### 2. 通知器修复（M11）具备工程价值

原问题是**状态不完整**（采集成功 ≠ 投递成功；单通道成功 ≠ 全通道成功；通知失败不能推进水位；无新告警 ≠ 无需重试），
现拆为 `run / collect.watermark / delivery`，引入稳定通知 ID 与 pending 重试 —— 已是小型可靠投递状态机。

退出码语义：`0` 正常 / `2` 采集失败 / `3` 投递失败 / `4` 状态写入失败。

**待关注**：

- 重试后重复投递是否可接受；
- **外部投递成功、内部状态未落盘时崩溃**如何处理（若无接收端幂等，不能宣称严格 exactly-once）；
- 通知 ID 的周窗口设计是否符合实际通知语义。

## 三、最大的架构问题：诊断结果需要结构化

不应把所有「无法给出明确结论」都塞进 `unknown`：

| 状态 | 含义 | 对普通人的下一步完全不同 |
|---|---|---|
| `unknown` | 没有匹配规则 | 查官方资料 / 问社区 |
| `insufficient` | 发现异常但**关键证据缺失** | 补证据 |
| `conflict` | 两个来源给出无法同时成立的结论 | 核对来源、时间、上下文 |
| `collection-failed` | 采集失败或未可信完成 | **先解决采集问题，不能当成零异常** |

**风险**：混在一起会产生一种很隐蔽的产品问题 —— **界面看起来很诚实，实际把不同的不确定性压扁了**。

建议先定**唯一数据契约**，再让报告 / UI / 通知 / 证据包共同消费：

| 字段 | 目的 |
|---|---|
| status | 当前判断状态 |
| evidence | 支撑结论的证据引用 |
| explanation | 候选解释 |
| confidence | 结论强度 |
| limitations | 缺失材料与适用边界 |
| nextAction | 建议下一步 |
| route | 处理对象 |

> 不必一次实现全部字段，但**先定契约**比继续加几十条规则更有长期价值。

## 四、UI：重点不是美观，是使用流程

现有：奶油紫 + 薄荷绿、开始扫描、搜索/过滤/排序、详情折叠、右键忽略、按程序统计、修复方案生成、一键检查、反馈入口。

**但**人工验收清单本身暴露了操作链过长：启动 → 扫描 → 等待 → 看表格 → 找异常 → 展开详情 → 读建议 → 决定找谁。

建议三层：

1. **首页 —— 我现在该怎么办？** 只显示当前状态、最重要的问题、建议下一步
2. **问题列表** —— 分组、重复次数、首次发生、影响对象、处理状态
3. **专业详情** —— 原始证据、错误码、规则来源、可信度、怎么验、修复风险、审计记录

⚠️ **设计红线**：不能把「没有发现问题」默认渲染成绿色。
采集失败 / 日志范围不完整 / 证据缺失时，首页应**优先呈现这些状态**，而不是给用户「电脑没问题」的错觉。

## 五、风险与待核实事项

### P0

**1. 修复器与建议之间的授权一致性**（需核对，未发现绕过）
- UI 中确认的目标与实际执行目标是否一致
- 生成的 `.cmd` 是否保留必要参数与风险提示
- `-Force` / `-Commit` / `-IUnderstandRisk` 是否存在**组合绕过**
- STOP、审计失败、执行前环境变化是否覆盖所有危险路径

**2. 真实用户首用测试**
- 人工验收清单的结果栏**目前为空**
- 需找一位不熟悉项目的非技术用户，观察能否：独立完成首次扫描 / 分辨正常·异常·unknown / 理解一条建议 / 找到正确下一步 / **拒绝自己不理解的危险操作**
- **测试前不要教用法**，否则会高估可用性

**3. 发布验证结果与实际发行包绑定**
- 包内 `tests/last-run.json` 记录 28/28、误诊漏诊 0/0、冒烟 PASS/PASS、lint 0 FAIL/0 WARN、时间 2026-10-23 13:15:36
- 但它是**包内自述**，不等于第三方复验；且未展示完整闭环，不能单独证明：
  - 当前 ZIP 与测试源码完全一致
  - 独立安装验证结果对应当前 ZIP
  - 测试是在**打包之后**执行的
  - 运行环境与第三方环境一致
- 建议用 `release.json` 绑定源码逐文件哈希 + 测试记录 + 构建时间 + 验证记录，并**明确测试在打包前还是打包后**

### P1

**4. L3 / WinRE 安全矩阵需独立维护** —— 采集成功 ≠ 采集正确。重点验证：
盘符重排误认目标盘 / BitLocker 锁定 / 输出盘空间不足 / 证据文件被截断 / 中途断电 / 目标盘只读与文件系统异常。
证据包完整性不能只查文件存在，要验 manifest、哈希、缺失条目与部分成功状态。
> **把另一个数据盘当成系统盘，可能比直接采集失败更危险。**

**5. 规则生命周期与证据质量** —— 每条规则应有：适用范围 / 原始来源与版本 / 最后验证时间 / 正例与负例 / 已知误报 / 兼容的 Windows 版本 / 状态（有效·待复核·弃用）。
> **不要把规则数量当作进展指标**；应统计：多少条有可复现证据、多少条建议被真人验证、多少条出现过真实误判。

**6. 本机数据与跨环境历史隔离** —— 避免把旧机器历史带到新机器误导用户；避免把历史记录、反馈次数误当成诊断可信度。
建议给历史记录加环境标识与数据版本，并区分：当前设备 / 导入的证据包 / 历史归档 / 外部反馈。

### 1. `tools/pack.ps1` 默认输出目录仍绑定开发机器


### 2. `tools/verify-package.ps1` 失败语义还需更严格

现做：临时解压 / 关键文件 / BOM / doctor / UI 自检 / 建议安全性。方向正确。

`$ErrorActionPreference = 'Continue'` + 靠退出码收集本身不错，但应审查：

- 解压失败是否稳定转为明确 FAIL
- 子进程启动失败是否被正确捕获
- **标准错误是否真正纳入诊断信息**
- 超时能否终止被测进程
- 临时目录是否**始终**清理
- 缺失 PowerShell 执行器是否明确失败
- 清理失败是否影响最终结论
- **说明写"做四件事"，与实际报告项数需一致**

建议把发布验证做成**独立结果文件**而非只打印 PASS，至少记录：
`包 SHA256 / 测试版本 / OS / PowerShell 版本 / 开始时间 / 结束时间 / 各项退出码 / 失败摘要`

现有 6 条为**自编样例**（非 SigmaHQ 真实规则、不含 Hayabusa 代码/规则、部分条件近似匹配、不支持的条件跳过、`why`/`do` 不照搬分析师语体）—— 处理正确。

**策略建议：暂时不要把 errwatch 做成规则平台。**
定位是「行业工具扩大专业分析能力，errwatch 降低普通人理解与行动门槛」。

**这 6 条应视为转换器测试资产，不算已获得真实故障覆盖能力。**

## 九、竞争力判断

**有一个值得继续验证的差异化方向，但还不能说已建立竞争优势。**

竞争力不在于：多几条规则 / 能否调用更多系统接口 / 能否进 WinRE / 再加几个修复按钮。

真正可能建立竞争力的是这条链：

`发现问题 → 解释问题 → 说明证据 → 判断边界 → 提供安全行动 → 确认结果`

即：**能明确告诉不做技术的人**发生了什么 / 为什么这么说 / 我还不知道什么 / 哪些事不要做 / 现在最合适的下一步是什么。

但最终取决于：真实用户是否愿意用、能否看懂、是否信任结论、下次出问题是否还会再打开它。

### 已改（源码层；下次打包生效）

**1. `tools/pack.ps1` —— 覆盖保护**

默认拒绝覆盖已有发行包，需显式 `-Force`。
实测：不带 `-Force` 重打同名包 → 打印「[拒绝打包] 已存在同名发行包」并 `exit 1`，原包 SHA-256 **未变**（`D553254F…1BDC`）。

**2. `tools/verify-package.ps1` —— 按契约重写**

| 维度 | 契约 |
|---|---|
| 检查四态 | `PASS` / `FAIL` / `SKIP` / `ERROR` |
| verdict 三态 | `PASS` / `FAIL` / `INDETERMINATE`（存在 ERROR ⇒ 不给完整结论） |
| verifierStatus | `ok` / `report-write-failed` / `aborted` |
| releaseGate | `allow` 仅当 verdict=PASS 且 verifierStatus=ok |
| 退出码 | `4` aborted > `3` 报告写入失败 > `1` 有 FAIL/ERROR > `0` 全通过 |
| 结果文件 | `<zip>.verify.json`（**包外**，避免发行包自证） |

三条铁律：① 拿不到退出码 = ERROR，**绝不默认 0**；② 报告写入失败只改 verifierStatus、不改 verdict，但退出码必须非 0；③ 写入失败时完整 JSON 打到 stdout 留痕。

真包回归：`verdict=PASS · verifierStatus=ok · releaseGate=allow · exit 0`，6 项全 PASS，`zipSha256` 与包一致。

**3. `tests\test-verify-package.ps1` —— 故障注入（8 用例，实测 8/8 PASS）**

| # | 注入 | 实测结果 |
|---|---|---|
| ① | 正常包 | exit 0 · PASS · ok · allow |
| ② | 损坏 ZIP（截断） | exit 1 · 解压 **ERROR** · INDETERMINATE · **未崩溃** |
| ③ | 缺关键文件（删 README） | exit 1 · FAIL |
| ④ | 子进程非零退出 | exit 1 · FAIL（exitCode=1） |
| ⑤ | 子进程超时（限 5s） | exit 1 · **ERROR「超时，已终止进程树」** · INDETERMINATE |
| ⑥ | 报告写入失败（测试通过） | exit 3 · **verdict=PASS 保留** |
| ⑦ | 报告写入失败（测试已 FAIL） | exit 3 · **verdict=FAIL 保留**（3 未抹掉失败事实） |
| ⑧ | 验证器自身中止（独占锁 zip） | exit 4 · **aborted** · INDETERMINATE · deny |

全部用「构造坏包 / 坏环境」触发，**产品脚本内无任何测试后门**。

### 顺带解决的进程管理问题（实测两轮）

| 轮次 | 方案 | 结果 |
|---|---|---|
| 一 | `Start-Process -PassThru` + `WaitForExit(ms)` | ❌ **证伪**：`ExitCode` 恒为 `<null>`；taskkill 后临时文件仍被占用 |
| 二 | 真 `Process` + `ReadToEndAsync()` + `Kill($true)` | ✅ 11/11：退出码可靠、超时判 `null`、**子进程树被清**（Job Object）、stdout+stderr 同捕、265 KB 不死锁 |

> 项目原注释「`-PassThru` + 重定向时 ExitCode 可能为 null（实测）」被复现证实 —— 该注释是对的。
