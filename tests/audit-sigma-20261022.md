# Sigma 规则转换：学习别人的方案，并把差距补上一截

- 日期：2026-10-22
- 起因：对标社区时发现的最大短板 —— 我们 **28 条手写规则** vs Sigma 生态**数千条**社区规则
- 做法：**学它的表达方式，然后单向转换过来**，不重造规则格式
- 结果：转换器可用、产物已接入 core、端到端验证通过（真实 evtx → 手工证据包 → 报告里出现 Sigma 规则命中）
- 过程中又抓出 **4 个真缺陷**（其中 1 个会造成大面积误诊）

---

## 一、从 Sigma 学到了什么（来源：官方文档）

抓到的规范：[sigmahq.io/docs/basics/rules.html](https://sigmahq.io/docs/basics/rules.html)

| 概念 | 内容 | 对我们的影响 |
|---|---|---|
| 三段结构 | `detection`（必填）/ `logsource`（必填）/ metadata（可选） | 转换时先做必填校验 |
| **list = OR，dict = AND** | YAML 的两种写法直接表达逻辑运算 | 这是转换的核心映射规则 |
| selection 组 + condition | 组间关系写在 `condition` 里（`a`、`a and not b`、`(a or b) and not c`） | 只支持前两种，复杂形式跳过 |
| 字段修饰符 | `\|contains` `\|startswith` `\|endswith` `\|re` `\|all` … | 支持前 5 种；其余（如 `\|base64offset`）跳过 |
| `level` | critical / high / medium / low / informational | 映射成**建议语气**，不编造处置方案（Sigma 本来就没有"怎么办"） |
| `falsepositives` | 官方明说**不参与转换**，只给人看 | 我们也不转，只在报告里提醒 |
| `condition` + filter 组 | 过滤要写成独立的组，而不是靠 falsepositives | 用负向断言 `(?!.*X)` 表达 |

**最有价值的一条认识**：Sigma 是**字段匹配**，errwatch 是**文本匹配** —— 两者不是同一种东西，
所以转换必然是近似的。既然如此，**有损就必须写在规则里**，而不是假装一一对应。

## 二、转换器的设计立场

| 立场 | 具体做法 |
|---|---|
| 有损就说明有损 | 每条转出的规则都带 `note`，写明"字段名已忽略""等值按包含处理"等近似点 |
| **宁可不转，不要转错** | 表达不了的条件一律跳过，并写明理由（一条转错的规则就是一次误诊） |
| 零依赖 | 本机没有 YAML 解析（pwsh 7.6 无 `ConvertFrom-Yaml`、Python 也没 PyYAML），所以自带一个覆盖 Sigma 子集的最小解析器 |
| 产物与手写规则分离 | 输出到 `core\rules-sigma.json`，不污染手写规则；加载时手写优先 |

新增能力：**按事件 ID 匹配**（`TranslateEvent`）。
事件日志本来就带结构化 ID，比在文本里猜可靠得多 —— 这也是 Sigma 规则能在我们这边生效的前提。

## 四、过程中抓到的 4 个真缺陷（都已修）

### 1. `$Input` 撞 PowerShell 自动变量

转换器最初的参数叫 `-Input`，而 `$Input` 是 PowerShell 的**自动变量**，会被静默清空 →
报错"无法将自变量绑定到参数 'LiteralPath'，因为它是空字符串"。
**教训**：参数/函数名别撞保留名（此前 `H` 撞 `Get-History` 别名也是同一类）。

### 2. 过滤组"无处附着"时被丢掉 → 规则变宽松

`sample-filtered.yml` 的 selection 只有 EventID 6008，filter 是 `Message|contains 'Windows Update'`。
转出来 `pat` 为空，**filter 直接丢了** —— 等于把"除更新引起的以外"变成"全部都算"，比原规则更宽松。
**修法**：filter 存在而 pat 为空 → **跳过该规则**（丢掉过滤 = 制造误报）。

### 3. 报告里"拿一个样本代表整组"

分析器按事件 ID 分组，把 `System` 的蓝屏 1001 和 `Application` 的 Codex 1001 混在一起，
再取组内第一个规则命中当作整组结论 —— 于是"蓝屏"那组显示的却是 Codex 服务事件。
**修法**：分组键改成「日志 + 事件 ID」；命中说法不一致时**如实列出分布**，不抽样代表。

### 4. 带事件 ID 的规则混进文本匹配 → AND 语义被拆散（最严重）

Sigma 规则里文本条件与事件 ID 是 **AND**（"7000 且 param1 含 service"）。
但 core 把**所有**带 pat 的规则都放进了文本匹配表 → `service` 这种宽泛词单独就会乱命中。
实测后果：`Application` 的 **1001** 事件被 **7000** 的服务规则命中了 **451 次**。

**修法**：规则表加 `TextMatch` 标记 —— **带事件 ID 的规则只走事件级匹配**（`TranslateEvent`），
不参与纯文本匹配。手写规则与纯关键词规则不受影响（回归仍 28/28）。

## 五、诚实记录

1. **样本是自写的，不是真实社区规则**：这次只用了 9 条我按规范手写的样本。
   **没有跑过 SigmaHQ 的数千条真实规则库**（github 抓不到，网络受限）。
   拿到规则库后重跑一条命令即可：`pwsh -File tools\sigma-convert.ps1 -Source <目录>`。
2. **YAML 解析器只覆盖子集**：不支持锚点/别名/流式写法，遇到就按普通字符串处理。
3. **近似点无法消除**（转换的本质）：字段名被忽略、等值按包含、AND 用 lookahead 表达（只保证"都出现过"）。
4. **`level` 只映射语气**：Sigma 没有"怎么办"，我们也没替它编。
5. **真实规则库的规模会暴露新问题**：几千条规则里会有更多不支持的形式，
   跳过率可能很高 —— 那正是转换报告要回答的问题，而不是"转得越多越好"。
