# 方案 vs 现状：逐条对账（2026-10-24，基线 `errwatch-20261024-aq`）

> 用途：用户给出的「errwatch 总方案」作为讨论基线，这里核的是**当前包里实际有什么**。
> 判定口径：**已实现** = 代码里有且测试看守；**部分** = 有骨架但缺方案要求的语义；**未实现** = 方案要的、代码里没有。
> 每条都给证据（`文件:行`），不给「我觉得」。

## 一、一句话结论

方案里 **5 个施工步骤有 3 个已经做完**（启动链、通知决策、状态契约），真正没做的是三件事：
**① 状态契约缺「诊断进度」这一维 ② 自动兜底/预授权完全不存在 ③ 保留策略与真实 CAD 演练欠着。**
另外方案里对「`register-watch` 仍注册旧 notify」的判断**已经过时**——那是 `-ah` 时期的状态。

## 三、三个需要你拍板的点

### 决策 1：第四维要不要加？（结构性问题，必须先定）

方案 §四 要求「诊断进度」成为事件的一个维度；现状是三维。

- 加：`ack-state.ps1` 的 `ValidateSet`、`STATE-CONTRACT.md` §一/§七 不变式、tray 的 `Add-Ack`、sentinel 的终态判定、`test-ack-state` 全要跟着改（**先定契约再改实现**）。
- 不加：则「事件在诊断第几步」只能从报告侧看，事件状态里查不到 —— 方案想要的「低风险取证持续跑、用户不必等完整诊断」就没有数据支撑。

我的判断：**加**，但要限定为「诊断是否至少完成一轮」的三个值（`not-started / collecting / complete`），不要把 `partial / failed` 塞进事件维度（那两个属于报告结论，已有五态）。维度越少越不容易乱。

### 决策 2：自动兜底现在做，还是等真实演练之后？

方案 §二 是这轮最大的新方向，但它有三个前置条件，现在**一个都不满足**：

1. 没有「兜底动作」的安全集合（哪些动作允许自动化，现在完全没定义）
2. 没有审计（自动执行必须留痕，`fix-audit.jsonl` 只覆盖修复器）
3. 真实 CAD 演练没做 → 不知道「保守兜底」到底能不能救回东西

建议：**先做「只提示不执行」的版本**——事件到期后托盘升级提示（「已 30 分钟未处理，建议先做 X」），把决策时限、动作白名单、审计三样建起来，执行留到演练之后。这样方案 §二 的骨架在，风险为零。

### 决策 3：保留策略和第四维一起做，还是先做保留策略？

保留策略（acks / events 滚动清理）是独立小活，但契约 §三 已经承诺了 7 天滚动，而代码没做 —— 属于「文档说做了、代码没做」，审计最容易挑。建议**先做它**（半天内可完），再动第四维。

## 五、附带核实（方案里点到、但容易误判的四处）

1. **`register-watch` 注册旧 notify**：方案沿用 `-ah` 的判断。现在是三任务双通道，`-Status` 还比对了启动项指向——**已过时，不必重做**。
2. **全屏守卫**：`Test-Fullscreen` 是主屏尺寸比较（M/P1-4 已知边界），多显示器/DPI/无边框仍不准；`test-tray` F/O 看守的是「策略生效」而不是「检测准确」。
3. **救援启动失败**：`tray:362-364` 写 `launch-failed`，且 `launch-failed` 不是终态（事件留在待处理）——符合契约。
4. **静默应用 ACK 重复写入**：`:508-512` 只在 `suppressed` 变化时写，P3-1 已修；`test-tray` 有对应用例。
