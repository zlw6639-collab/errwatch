# 审计：明确的停止方式 + 重启助手 + 真实链路验证（2026-10-24）

> 起因（两个真实问题，不是设想）：
> 1. 改了哨兵/托盘代码之后，**磁盘上的新代码不会自动生效** —— 旧进程内存里还是旧版本；
>    而任务管理器里一堆 `pwsh.exe` 分不清哪个是哨兵，手动结束很容易杀错（比如杀掉 DSH 自己）。
> 2. 方案 §六 要求「提供明确的停止、退出和注销常驻任务的方式」—— 此前**没有**，只能杀进程。

## 一、这次补的三样

| 能力 | 实现 | 为什么必须 |
|---|---|---|
| `-Stop` 优雅停止 | 写 `sentinel-stop.flag`，主循环下一轮消费并退出；`-Stop` 最多等 15 秒，超时**删掉标记**并报失败（免得污染下次启动） | 没有它只能杀进程；用户和脚本都没法「正常地停」 |
| `-InstanceName` | 单实例 Mutex 名后缀，默认空 = 生产实例 | 测试实例要在「现役哨兵正在跑」的机器上验证新逻辑，否则永远撞 Mutex |
| `-RetentionEveryHours` | 保留策略最小间隔，默认 6 小时 | 真实链路验证需要在一分钟内看到清理发生，而不是等 6 小时 |
| `errwatch-restart.ps1` + `重启看护.cmd` | 按**命令行**精确匹配 `errwatch-sentinel.ps1` / `errwatch-tray.ps1`，只动这两个进程，再用启动项 `.vbs` 拉起 | 重启不该靠「杀所有 pwsh」这种赌命的做法 |

## 二、踩到的坑（真踩了，不是预防性写）

**重启脚本第一版会把「没重启成功」判成成功。**
它用「心跳时间 < 5 秒」当成功条件，但**刚被停掉的旧进程留下的心跳时间戳本来就很新**——
新进程还没起来，检查就已经通过。本机实测：哨兵明明没起来，脚本报 `[OK]`。

修法：改成比较**心跳时间戳是否前进**（`$hb -gt $hbBefore`），而不是「够不够新」。

## 三、真实链路验证（`tools\verify-retention-live.ps1`，7/7）

单测证明**规则**对；这个脚本证明**接上了**。它真起一个哨兵进程、真杀一个被监视进程：

```
  [PASS] 终态超 7 天的事件被真实清理
  [PASS] 它的 ACK 被协调清理
  [PASS] 清理结果写进了 sentinel-retention.jsonl
  [PASS] 杀掉被监视进程后产生真实事件
  [PASS] 真实事件类型是 ProcessExit
  [PASS] 未满 7 天的真实事件没有被清理
  [PASS] -Stop 能让真实哨兵优雅退出
```

- 全程在临时 `-StateDir` 里跑，**不碰生产状态文件**
- 被监视进程用系统自带 `PING.EXE`（无窗口、易结束、不碰用户程序）
- 「9 天前事件 / 8 天前终态」那条是手工写的，但**清理是真实哨兵进程执行的** ——
  这正好回答「规则只在夹具上跑过」的疑问：规则对 + 真实路径通。

## 四、生产实例真的重启了

| 步骤 | 结果 |
|---|---|
| 重启前 | 哨兵 PID 20736 / 托盘 11068（跑的是旧代码） |
| `errwatch-restart.ps1` | 结束 20736 + 11068 → 用 `.vbs` 拉起 → 心跳恢复 |
| 新实例 | 哨兵 20144 / 托盘 25168 |
| `-Stop` 对生产实例 | ✅ 「哨兵已退出（停止标记已被消费）」，心跳停更新 |
| 再拉起 | ✅ 心跳前进，`sentinel-error.log` 不存在（无异常） |

> 注：DSH 会话一开始**看不到**哨兵 PID（进程枚举被作业对象限制），拿到 PID 是环境放开之后的事。
> 这也是为什么「重启助手」必须做成用户可双击的脚本 —— 不能假设代理总能操作进程。

## 六、剩余

1. `-Stop` 只对**新版本**哨兵有效。升级那一刻若旧版本还在跑，必须先跑重启助手 ——
   这是「升级路径」的固有约束，已写进 `-Stop` 的失败提示与重启脚本注释。
2. `重启看护.cmd` 没有在「杀软拦截 `.vbs`」的机器上验证过（已知边界，见 HANDOFF 27–33）。
3. 托盘被重启时会丢当轮 UI 状态（菜单展开状态）；观察数据都在文件里，不影响功能。

## 七、补充（2026-10-24 晚）：一个会**杀掉父进程**的真 bug

现象：`errwatch-restart.ps1` 偶尔返回 `4294967295`（-1），且没有任何输出 —— 看起来像脚本自己崩了。

真相：脚本按「命令行里包含 `errwatch-tray.ps1`」找目标进程，而**任何碰巧提到这个文件名的 pwsh 都会命中**，
包括**调用它的父进程**。我实测时命令里恰好写了 `errwatch-tray.ps1 -Check`，
于是整段 `-Command` 字符串命中 → 脚本把父进程杀了 → 工具层只看到 -1。

风险不止于此：用户如果开着编辑器/终端、命令行里恰好出现过这些路径，也可能被误杀。

修法（两道保险）：

1. **排除自身与所有祖先进程**（沿 `ParentProcessId` 上溯，最多 32 层）
2. **收紧正则**：必须是实参形式 `-File "...\errwatch-(sentinel|tray).ps1"`，而不是任意出现

验证：在同一条命令里故意写着 `errwatch-tray.ps1 -Check` 再跑，`exit=0`，且多余的托盘实例被清掉
（之前因为反复重启攒了 2 个托盘）。

> 教训：**「命令行包含某字符串」是最脆弱的进程识别方式之一**，因为它把「我提到它」和「我是它」混为一谈。
> 这跟 M60 那条「用本地化文案判断零事件」是同一类错误：拿一个**间接、可被意外满足**的信号当判据。
