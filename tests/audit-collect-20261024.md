# 审计：采集状态误判（2026-10-24，接手后第一件事）

> 结论一句话：**弹窗通道在本机已经静默失效 6 小时，而所有门禁都是绿的。**
> 根因不是逻辑写错，是**判定依据写成了本地化文案**，而真实文案多了一个「任何」。
> 修复后 `run.ps1` 28/28 · 采集状态 11/11 · 全专项绿 · 基线 78 一致。

## 一、故障链（都是本机实测，不是推测）

| 时刻 | 事实 | 证据 |
|---|---|---|
| 2026-10-23 18:05 | 最后一次成功的检查 | `last-check.json.collect.watermark = 18:05:16`（之后再没推进） |
| 18:05 起 | 每 2 分钟一次检查，每次都「失败」 | `lastExit=2` / `phase=collect-failed`；哨兵 `-NotifyEveryMinutes 2` 代跑 |
| 期间 | **不弹任何窗**（失败分支 `exit 2` 在告警处理之前返回） | `errwatch-notify.ps1` 采集失败分支 |
| doctor | 显示「[失败] 上次检查没有完成」 | 用户看到的是「检查失败」，不是「没有错误」 |
| 2026-10-24 00:27 | 修复后实跑一次 | `exit 0`、`lastExit=0`、`phase=done`、watermark 推进到 00:27 |

`last-check.json` 里记的原文：

```
failure = Application: 找不到任何与指定的选择条件匹配的事件。; System: 找不到任何与指定的选择条件匹配的事件。
```

## 二、根因

三处采集出口都用「异常文案」判断「零匹配 vs 真失败」：

- `errwatch-notify.ps1`：`'No events were found|没有事件|no events|找不到与指定的选择条件匹配'`
- `errwatch-timeline.ps1`：`'No events were found|没有事件'`
- `errwatch.ps1`：`'找不到与指定的选择条件匹配的事件|No events were found'`

而真实运行路径抛的是「找不到**任何**与指定的选择条件匹配的事件」—— 差「任何」两个字，正则不命中。
后果不是异常，而是**把「本机没有错误」记成「检查失败」**：水印不推进（窗口一路膨胀）、
弹窗不触发（该报的错不报）、doctor 常红（用户以为工具坏了）。

值得单独记一笔：这条正则能匹配 **PowerShell 7 的文案**（「找不到与指定的选择条件匹配的事件。」）
和**英文文案**，所以「在 7 下手工跑一次」看起来完全正常 —— 这正是它能潜伏下来的原因。
生产路径是 5.1（哨兵用 `System32\WindowsPowerShell\v1.0\powershell.exe` 代跑），
只有在那条路径上才会抛中文变体。

## 三、为什么全绿的门禁没拦住

- 没有任何测试覆盖「采集失败 vs 零事件」的判定（`grep NoMatchingEventsFound tests\` 为空）；
- `-Simulate collect-fail` 只验证「失败时如实上报」，不验证「零事件不能被当成失败」；
- 上一轮的「假绿」教训（⑥ 号测试改真实模板驱动）针对的是崩溃字段解析，这一条同类问题没被顺带扫到。

## 四、修法

1. **判定收进 core**：新增 `core\Test-ErrwatchNoEventError`（唯一实现），
   依据 `FullyQualifiedErrorId = NoMatchingEventsFound` / `Category = ObjectNotFound`（跨语言稳定），
   文案只作兜底并把变体写全（`找不到(任何)?与?指定的选择条件匹配`）。
2. **三处出口改调用 core**，禁止再各自写文案正则。
3. **水印上限**：`(now - since) > MaxAgeHours` 时截断到 `now - MaxAgeHours`
   —— 防止上一版误判留下的积压窗口在恢复后一次扫 6 小时以上、把过期错误重新弹一遍。
4. **新增测试** `tests\test-collect-state.ps1`（11 项），并接入 `run.ps1`：
   - A1/A2：**真实异常对象**（未来时间窗 → 必然零匹配）必须判为「零事件」；
   - B1/B2/B3：中文「任何」变体 / 中文旧文案 / 英文文案；
   - C1/C2/C3：拒绝访问、日志服务未启动、空记录 —— 不能被吞成「零事件」；
   - D：三个出口都必须调用 core 判定，且**不允许再出现裸文案正则**（防「顺手再加一条关键字」复发）。

## 五、反证（测试会咬人）

把 core 判定退回旧正则（只有文案，没有「任何」），在副本里跑新测试：

```
[FAIL] B1 中文「找不到任何…」+ NoMatchingEventsFound（本机实跑形态）
采集状态判定：10 通过 / 1 失败
exit=1
```

还原后 11/11。说明这条测试**不是**改前改后都绿的摆设。

## 七、剩余

1. **这条 bug 的真正教训没被自动化**：现在看守的是「三处出口都调用 core」，
   但没法看守「任何新写的异常判定都不许依赖本地化文案」。可考虑在 lint 里加一条规则。
2. **`last-check.json` 的 `failure` 字段会留在历史里**：本轮之后第一次成功已覆盖为 `null`，
   但如果用户在 18:05–00:27 之间真出过错误，那段时间的错误确实**没有被弹窗**（可能仍在事件日志里，未核）。
3. 待办 27（`tray-acks.jsonl` 保留策略）仍未做 —— 与本条无关，但同属「长期跑会攒坏」的一类。
