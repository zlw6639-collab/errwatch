# 审计：五项可观测指标（2026-10-24，方案 §七）

> 背景：`tests/audit-plan-vs-current-20261024.md` §七 第 16 条明确写着**「未定义」**——
> 此前只有「测试通过数」与 `last-check.json`，没有按五项组织的观测口径。
> 没有口径就只能说「门禁全绿」，说不出「发现要多久 / 救援成不成 / 噪音多不多」。

## 一、五项口径（先定定义，再写代码）

| # | 指标 | 定义 | 数据来源 | 诚实的局限 |
|---|---|---|---|---|
| 1 | **发现** | 上一次看到该进程 → 判定它消失（秒） | `sentinel-events.jsonl` 的 `detectedAt - lastSeenAt`；`sentinel-status.json` 的 `latencySamplesMs` 兜底 | 受轮询间隔限制，是**上界近似**，不是崩溃的精确时刻 |
| 2 | **触达** | 发现 → 托盘写出 `notify=attempted`（秒） | 事件 × `tray-acks.jsonl` | 只统计**真的发过通知**的事件；被抑制的不算 |
| 3 | **决策** | 发现 → `lifecycle` 进入终态（秒） | 事件 × ACK | 用户一直不处理就没有样本，单独报「仍在待处理」 |
| 4 | **恢复** | 有救援记录的**事件**里，到 `user-confirmed`/`verified` 的比例 | `tray-acks.jsonl` 的 `rescue` 维度 | 分母是事件数不是 ack 行数（同一事件可先 launching 再 verified） |
| 5 | **安全** | 被抑制数 / 人工标「没有可操作的」/ 覆盖缺口 | ACK `notify=suppressed` + `feedback.jsonl` + `sentinel-coverage.json` | 「没有可操作的」是**人工信号**，不叫「误报率」 |

**一条贯穿原则**：没有样本就显示「量不出来」，**绝不显示 0**。
0 秒会被读成「延迟为零」，0% 会被读成「全失败」——两种都是误导。

## 二、实现

| 文件 | 作用 |
|---|---|
| `core/metrics.ps1` | 唯一实现：`Get-ErrwatchMetrics -Root -Days`。只读，不写任何文件 |
| `errwatch-metrics.ps1` | CLI：人话（默认）/ `-Json`（机器可读）/ `-Days N` / `-Root`（只换数据目录，core 永远从脚本目录加载） |
| `tests/test-metrics.ps1` | 6/6 口径测试（见 §四） |

两个容易写错的地方，已经在代码里定死：

1. **`-Root` 不能同时当 core 目录**：测试用临时数据目录时，若 core 也从该目录加载会直接「核心层缺失」。
   实现里拆成 `$dataRoot`（`-Root`）与 `$coreRoot`（`$PSScriptRoot`）。
2. **feedback 也要按窗口过滤**：否则「累计人工反馈」和「本期抑制数」混口径。

## 六、剩余（诚实记录）

1. **没有真实故障样本**：四项延迟指标当前全部「量不出来」。要等真实崩溃演练（下一步）才有数。
2. **「恢复成功率」只认用户确认**：`user-confirmed` / `verified` 都来自用户自检或事件核验回写，
   没有客观验证「文件内容真的完整」——那需要打开文件比对，超出只读边界。
3. **误报没有自动判定**：现在只有人工反馈信号（「没有可操作的」）。要自动判误报必须知道「基准真值」，
   而崩溃场景下真值不可得，所以不做，避免造一个看似精密的假指标。
4. **没有 UI 入口**：目前只有 CLI。要不要进设置窗「工具」页，等真实数据出来再决定（现在界面里没有可看的东西）。
